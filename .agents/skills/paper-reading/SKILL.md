# 论文阅读

把一篇论文读成一份**可供真人快速确认的标注草稿**。目标是把确认人的工作量从“通读全文”降到“核对几处关键判断”。你起草，人确认。

## 不可违反的规则

1. **绝不确认。** 你产出的每一行 `status` 都是 `待确认`，`confirmed_by` 和 `confirmed_at` 留空。即使用户让你“顺便确认”，也要说明确认必须由真人对照原文完成，并指给他们 CONTRIBUTING.md 的第 3 步。
2. **如实报告读了多少。** 读到全文、部分全文还是只有摘要，按实际情况填 `reading`。工具截断了正文、附录没读到、PDF 打不开，都要明说。
3. **每个判断附出处。** `R`、`feedback`、`loop`、`evidence` 四项必须给出原文的章节或页码，加一两句引文。找不到出处就标 `待核对`。
4. **不推断。** 论文没写的内容不要补。验证成本没报告就填 `未报告`，不要根据评估器类型猜。
5. **不改分类法。** 论文归不进现有的领域、子类或取值时，照最接近的填，并在“需要你核对的点”里提出，由维护者决定是否新增。
6. **不替人取舍。** 是否收录、有争议的归类，列出两种读法各自的依据，交给人定。

## 步骤

### 1. 取原文

优先拿 PDF 全文（arXiv 用 `https://arxiv.org/pdf/<编号>`）。拿不到全文时退到摘要页，并把 `reading` 记为 `仅摘要`；这种情况下判断类字段多数应为 `待核对`。

### 2. 查重

在 `data/papers.tsv` 里按链接和标题查找。已收录就告诉用户编号，转为“复核已有标注”：对照原文逐项检查现有取值，报告不一致之处。

### 3. 带着七个问题读

- 系统在迭代中改了自身的什么？（提示、记忆、技能；脚手架或自身代码；权重；改进过程本身；还是只改外部产物）
- 改动是否被保留并在后续轮次或任务中复用？
- 用什么信号判断一次改动是否更好？
- 回路里人的角色是什么？跑了多少轮？
- 改进在哪里被证实：只在训练或调优所用的任务上，还是在留出的或其他任务上？有没有独立评测？
- 论文怎么称呼自己：递归自我改进、自我改进或自演化，还是都没有？它有没有明确否认？
- 实验做的是什么任务？属于哪些应用领域？

同时留意论文自己报告的失败：评估器被钻空子、性能在若干轮后下降、目标漂移。

### 4. 按规则取值

逐字段判定的规则、界线案例和常见误判见 [references/annotation-rules.md](references/annotation-rules.md)。取值前先读它。枚举字段的允许取值以 `scripts/check_data.py` 为准。

### 5. 对照已有清单校准

从 `data/papers.tsv` 里找出最相近的两三篇（同子类，或做法相似），比较 `R`、`feedback`、`evidence` 的取值。如果你的判断和相近论文的口径不同，要么调整，要么在核对要点里说明为什么这篇不一样。

### 6. 输出

按下面的格式输出，顺序不要变：

```
## <论文简称>：<一句话说明它是什么>

阅读情况：<全文 / 部分全文 / 仅摘要>。<没读到的部分>

### 标注草稿
| 字段 | 取值 | 出处 |
| --- | --- | --- |
| 领域标签 | ... | 实验任务：第 x 节 |
| 子类 | ... | |
| 纳入标准 | 闭环；自指；累积 | |
| 改进对象 | ... | 第 x 节 |
| 自指深度 | R? | 第 x 节：“原文引文” |
| 反馈来源 | ... | 第 x 节：“原文引文” |
| 闭环程度 | ... | ... |
| 累积方式 | ... | ... |
| 改进轮数 | ... | ... |
| 验证成本 | ... | ... |
| 失败可逆性 | ... | ... |
| 自称程度 | ... | 标题或摘要 |
| 证据强度 | ... | 第 x 节 |
| 主要结果 | ... | 表 x |
| 失败与局限 | ... | ... |
| 置信度 | 高 / 中 / 低 | |

### 需要你核对的点
1. <最没把握的判断>：<为什么拿不准>。去看 <章节或页码>。
2. ...（3 到 5 条，按重要性排序）

### 与已有清单的对照
- 最相近：P0xx <简称>（R?，<反馈来源>）。<口径是否一致>

### 对综述有用的信号
- <自称与证据的落差 / 论文报告的失败 / 可能的反例；没有就写“无”>
```

“需要你核对的点”是最重要的部分。写具体：不要写“请核对自指深度”，要写“系统改的是工具库还是调用工具的代码，决定它是 R1 还是 R2；3.2 节的描述两种读法都说得通”。

### 7. 写入仓库（仅当用户要求）

1. 在 `data/papers.tsv` 末尾追加一行，列顺序见表头，`status` 为 `待确认`，文本字段里不能有 `|`。“出处”写进 `r_evidence`（自指深度）和 `notes`（其他）。
2. 运行 `python3 scripts/check_data.py`，再运行 `python3 scripts/build_readme.py`。
3. 告诉用户这一行还需要真人按 CONTRIBUTING.md 第 3 步确认。不要自己把它改成已确认。

如果用户是通过 Issue 表单提交的，改用 `scripts/issue_to_row.py`，然后对照原文检查表单里的取值，把你的不同意见列在核对要点里。
